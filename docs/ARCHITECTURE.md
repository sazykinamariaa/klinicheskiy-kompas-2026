# Архитектура «Клинического компаса»

## Принципы

1. **Клиническое содержание — только в конфигурации** (`config/*.json`). Код не содержит порогов, текстов для пациента, доз и правил. Любое значение имеет статус (`confirmed`, `approved_by_physician`, `verify`, `waiting`, `draft_by_dev_pending_review`); незавершённое честно показывается в панели администратора и в карточке.
2. **Система предлагает, врач решает.** Результат движка — только предложения. `TherapyOrder`, `Referral`, `StatusChange` создаются исключительно в `app/proposals.py` по решению лечащего врача (подтвердить / изменить / отклонить с причиной). Тест `test_orders_created_only_in_proposals_module` сканирует исходники и падает, если такая сущность создаётся где-то ещё.
3. **Неизвестное остаётся неизвестным.** Логика трёх значений (да / нет / неизвестно). Неизвестный факт никогда не превращается в «противопоказаний нет»: проверка препарата получает состояние «Проверка безопасности не завершена».
4. **Безопасность выше удобства.** «Затрудняюсь ответить», пропуск или прерванный блок вопросов безопасности не снижают уровень; красный — только по подтверждённым ответам.

## Стек и почему

| слой | выбор | причина |
|---|---|---|
| Бэкенд | Python 3.11+, FastAPI | типизированный API, автоматический OpenAPI (требование метрик), быстрый ввод правил на Python |
| БД | SQLite (WAL, `synchronous=FULL`) для демо; те же модели работают на PostgreSQL через `KK_DATABASE_URL` | запуск одной командой; переход на Postgres без смены кода |
| Очередь | таблица `outbox` в той же БД + фоновый поток | уведомление и алерт фиксируются **в одной транзакции** (нет потери при сбое); не нужен брокер для демо |
| Шифрование | Fernet на уровне поля (`EncryptedText`) | персональные данные и свободный текст зашифрованы при хранении |
| Интерфейс | React/Vite PWA (следующий этап) | одно приложение для врача (десктоп) и пациента (телефон) без установки из магазина |

## Модули `backend/app`

* `expr.py` — разбор условий из конфигурации (`when`/`check`): AND/OR/NOT, сравнения, `in [...]`, `delta(scale, 14d)`, `days_since(field)`, ссылки на правила `R-RED-*`. Вычисление трёхзначное (Клини).
* `config_loader.py` — загрузка и проверка конфигурации; отчёт об исполнимости правил; список «ЖДЁМ».
* `scales.py` — подсчёт шкал по `scales.json` (сумма, подшкалы LSAS, неполные ответы без итога, пункт 9 PHQ-9).
* `facts.py` — единый словарь фактов из состояния пациента (анкета, шкалы, профиль врача, чек-ин, приверженность).
* `rules.py` — алерты и маршрутизация; `drug.py` — проверка препарата (противопоказания > взаимодействия требуют решения > вне показаний > проверка не завершена > показан, ждёт врача); `engine.py` — объединение; `monitoring.py` — динамика, предложения статусов.
* `alerts_service.py`, `queue.py`, `worktime.py`, `clock.py` — жизненный цикл алертов, доставка, рабочее время (из `clinic_settings.json`), подменяемые часы для тестов.
* `proposals.py` — единственный путь к назначению, направлению, статусу.
* `summary.py`, `pdfexport.py` — сводка для психиатра (JSON, FHIR-подобный Bundle, PDF).
* `importer.py` — импорт истории: кандидаты правилами, принимает врач.
* `routers/` — API по ролям: `patient`, `doctor`, `doctor_extra`, `alerts`, `psychiatrist`, `admin`, `info` (источники, интеграция), `auth`.

## Модель данных (29 таблиц)

Пользователи и роли (`patient | doctor | duty | psychiatrist | admin`, у дежурных `duty_role`), пациент и связка «врач — пациент», приглашение и согласие; анкета, прохождения шкал, уточняющие вопросы безопасности, чек-ины, приверженность, нежелательные явления; версии полей клинического профиля; алерты и их журнал; предложения и решения; назначения, направления, статусы; сообщения, «Мой план», цель, доверенный контакт; очередь и журнал уведомлений; журнал аудита; импорт.

## Алерт-пайплайн

```
ответы/данные → facts → rules.evaluate → alerts[] → alerts_service.sync_alerts
   красный : outbox.notify (врач + ответственный, push+SMS, сразу, круглосуточно)
             outbox.escalate +5 мин → дежурный врач, +10 мин → администратор смены
   оранжевый: в рабочее время сразу; вне его — на начало следующего рабочего дня,
             дежурному информационное уведомление, пациенту честный текст про рабочие часы; +120 мин → дежурный
   жёлтый  : в приложении
сбой канала: повторы 5/15/60/300/900 с → запасной канал → эскалация дежурному
принятие алерта отменяет плановую эскалацию; «не удалось связаться» красный алерт не закрывает
```

Идемпотентность: повторная оценка тех же данных не создаёт дублей (`open_key` у алерта, `idempotency_key` у задачи). Захват задачи — compare-and-set с «арендой», два обработчика не возьмут одну задачу.

## Роли и доступ

Пациент видит только свои данные и спокойные тексты (названий уровней, номеров правил и красного цвета нет). Врач — только своих пациентов. Дежурные видят алерты всех пациентов (красный не ждёт лечащего врача). Психиатр — подтверждённые направления со сводкой. Администратор управляет конфигурацией, очередью и пользователями, клинических данных не видит; в журнале аудита ему доступны только время, роль и действие.

## Что намеренно упрощено в демо

SMS/push — заглушки с имитацией сбоев; МИС — заглушка адаптера; один процесс и SQLite. Для боевого режима: PostgreSQL, внешний провайдер уведомлений, отдельный воркер очереди (код тот же), хранение ключа шифрования в менеджере секретов.
